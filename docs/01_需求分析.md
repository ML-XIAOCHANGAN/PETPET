# PETPET 安卓虚拟宠物社区需求分析

> 文档状态：首版规划稿  
> 编写日期：2026-08-09  
> 适用阶段：产品确认、原型设计、技术预研

## 一、产品概述

PETPET 是一款面向安卓手机的社区型虚拟宠物软件。每位用户只能领养一只固定外观的小猫。小猫可以悬浮在其他应用上方，用户通过每天聊天和简单互动增加好感度，同时可以进入社区发布和浏览宠物相关动态。

首版的核心不是复杂养成，而是建立“手机里一直陪着我的小猫”和“与其他主人分享日常”两种体验。

## 二、已确认需求

以下内容直接来自用户本次说明，作为首版不可随意扩张的范围：

1. 软件运行在安卓手机上。
2. 产品定位偏社区。
3. 每位用户可以获得并领养自己的虚拟宠物。
4. 首版只提供一种宠物，外貌为小猫头像。
5. 每个账号只能领养一只宠物。
6. 每天陪小猫聊天可以增加好感度。
7. 与小猫互动可以增加好感度。
8. 不制作换装系统。
9. 不制作成长或进化系统。
10. 不制作小游戏。
11. 软件开启相应功能后，小猫位于其他手机界面之上。

## 三、关键解释与规划假设

### 3.1 “位于最上层”的解释

首版将其实现为安卓悬浮窗，而不是强制让整个应用始终占据前台：

- 用户主动授予“显示在其他应用上层”权限后，小猫头像可显示在其他应用上方。
- 小猫头像可拖动、贴边停靠、点击互动。
- 用户可以从悬浮窗或系统常驻通知中暂停、隐藏或关闭小猫。
- 未获得权限时，应用本体仍可正常使用，不反复强迫用户授权。
- 首版不默认开机自启，避免耗电、打扰用户及增加上架审核风险。

### 3.2 “社区向”的首版解释

社区首版采用最小可用范围：

- 动态广场；
- 发布文字或图片动态；
- 点赞；
- 评论；
- 举报；
- 拉黑；
- 用户主页及其领养的小猫信息。

首版暂不加入私信、群聊、直播、排行榜和宠物交易。这些功能会明显增加内容治理、骚扰防控和服务成本。

### 3.3 “聊天”的首版解释

聊天以自然语言宠物陪伴为目标，推荐由服务端接入可替换的对话模型，同时保留本地预设回复作为断网或服务异常时的降级方案。客户端不得保存模型服务密钥。

具体模型供应方、每人每日消息额度和内容审核服务需要在开发启动前确认。

## 四、目标用户与产品价值

### 4.1 目标用户

- 喜欢猫咪、轻量陪伴和可爱桌面元素的安卓用户；
- 不愿投入大量时间进行复杂养成，但愿意每天短暂互动的用户；
- 愿意分享虚拟宠物日常、情绪或生活片段的社区用户。

### 4.2 核心价值

- **陪伴感**：小猫不只存在于应用页面内，也能出现在日常手机使用场景中。
- **低负担**：每天聊几句、摸一摸即可建立持续关系。
- **共同话题**：所有人从同一种小猫出发，通过名字、聊天和动态形成个人故事。

## 五、首版用户流程

1. 用户首次打开软件，阅读隐私政策并登录或注册。
2. 用户进入领养页，看到唯一的小猫形象。
3. 用户为小猫取名并确认领养。
4. 服务端创建唯一宠物记录，领养完成后不可重复领养。
5. 应用说明悬浮功能用途，并由用户主动跳转到系统授权页面。
6. 授权成功后，小猫头像显示在其他应用上方。
7. 用户点击小猫，可以选择聊天、互动、进入主页或暂时隐藏。
8. 当天首次满足条件的聊天和互动增加好感度。
9. 用户进入社区浏览、发帖、点赞或评论。

## 六、功能需求

### 6.1 账号与身份

| 编号 | 功能 | 首版要求 |
| --- | --- | --- |
| 账号-01 | 注册和登录 | 支持一种稳定登录方式；正式开发前确定手机号、邮箱或第三方登录 |
| 账号-02 | 登录状态 | 安全保存登录凭证，凭证失效后引导重新登录 |
| 账号-03 | 用户主页 | 显示昵称、头像、简介、小猫名字和公开动态 |
| 账号-04 | 注销账号 | 提供清晰入口，并按隐私规则处理个人数据和公开内容 |

社区包含用户生成内容，因此不能仅使用无法追责的永久游客身份。可提供试玩，但发帖、评论和领养前必须完成正式登录。

### 6.2 领养系统

| 编号 | 功能 | 首版要求 |
| --- | --- | --- |
| 领养-01 | 宠物展示 | 只展示一种固定小猫头像 |
| 领养-02 | 宠物命名 | 用户可以输入名称，需限制长度并过滤违规词 |
| 领养-03 | 唯一领养 | 一个账号最多存在一条有效宠物记录，由服务端和数据库共同约束 |
| 领养-04 | 重复请求 | 重复点击或网络重试不能创建第二只宠物 |
| 领养-05 | 放弃与更换 | 首版不提供放生、换宠物和重置功能 |

### 6.3 悬浮小猫

| 编号 | 功能 | 首版要求 |
| --- | --- | --- |
| 悬浮-01 | 权限引导 | 清楚解释权限用途，必须由用户主动授权 |
| 悬浮-02 | 顶层显示 | 授权并开启后，小猫显示于其他应用上层 |
| 悬浮-03 | 拖动停靠 | 可拖动，松手后自动贴近屏幕左右边缘 |
| 悬浮-04 | 点击菜单 | 提供聊天、互动、进入应用、隐藏和关闭入口 |
| 悬浮-05 | 状态记忆 | 记住最近位置和开启状态；系统不允许时安全降级 |
| 悬浮-06 | 常驻说明 | 使用前台服务时展示可理解、可操作的常驻通知 |
| 悬浮-07 | 防误触 | 拖动过程不触发点击；不遮挡系统导航和关键操作区域 |

小猫悬浮窗应保持轻量，静止时不进行高频动画或轮询。屏幕关闭后暂停不必要更新，以减少耗电。

### 6.4 聊天系统

| 编号 | 功能 | 首版要求 |
| --- | --- | --- |
| 聊天-01 | 对话入口 | 可从悬浮小猫和应用内宠物主页进入 |
| 聊天-02 | 文本聊天 | 用户发送文字，小猫以稳定的猫咪性格回复 |
| 聊天-03 | 上下文 | 首版只保留有限轮次上下文，避免无限增长 |
| 聊天-04 | 好感奖励 | 每天有效聊天达到条件后增加好感度 |
| 聊天-05 | 防刷 | 重复字符、空消息、极速发送和机器请求不计奖励 |
| 聊天-06 | 安全回复 | 对违法、自伤、骚扰等高风险内容采用安全策略和必要提示 |
| 聊天-07 | 服务降级 | 模型不可用或断网时使用预设回复，并明确当前状态 |

建议的首版好感规则：当天累计完成三轮有效对话后增加 `5` 点，每天最多因聊天获得一次奖励。该数值是规划建议，开发前可调整。

### 6.5 互动与好感度

首版互动保持简单：点击“摸摸小猫”后播放短反馈动画或表情，并增加好感度。

建议规则：

- 每次有效互动增加 `1` 点；
- 每日最多有 `5` 次互动计入好感度；
- 超过上限仍可互动，但不再加分；
- 好感度由服务端计算并落库，客户端只显示结果；
- 好感度只体现亲密程度，不触发成长、进化、换装或能力变化；
- 首版好感度只增不减，避免签到式惩罚造成负担。

### 6.6 社区

| 编号 | 功能 | 首版要求 |
| --- | --- | --- |
| 社区-01 | 动态流 | 按时间与基础热度展示公开动态，支持分页加载 |
| 社区-02 | 发布 | 支持文字及最多若干张图片，数量和大小由服务端配置 |
| 社区-03 | 点赞 | 同一用户对同一动态只能保留一次点赞状态 |
| 社区-04 | 评论 | 支持一级评论；首版不做无限楼中楼 |
| 社区-05 | 删除 | 用户可删除自己的动态和评论 |
| 社区-06 | 举报 | 可举报动态、评论和用户，记录原因与处理状态 |
| 社区-07 | 拉黑 | 拉黑后双方内容和互动按规则隐藏 |
| 社区-08 | 内容审核 | 发布前或发布后进行文本、图片审核，并提供人工管理入口 |
| 社区-09 | 空状态 | 无内容、无网络、审核中和加载失败均有明确提示 |

### 6.7 通知

首版只保留必要通知：

- 悬浮服务运行中的常驻通知；
- 动态收到评论或点赞后的站内消息；
- 管理员对举报或违规内容作出处理后的站内消息。

不使用高频“宠物想你了”推送。普通通知应由用户选择是否授权和关闭。

### 6.8 管理后台

社区产品必须配套最小管理能力：

- 用户查询、限制发言和封禁；
- 动态与评论查询、下架和删除；
- 举报队列及处理记录；
- 敏感词和基础运营配置；
- 模型用量、失败率和异常请求查看；
- 管理操作审计日志。

## 七、页面与导航结构

建议底部导航使用三个入口：

1. **小猫**：宠物状态、聊天、互动、好感度和悬浮窗开关。
2. **社区**：动态广场、发布、详情、评论和举报。
3. **我的**：个人主页、消息、黑名单、隐私、权限和账号设置。

首次使用时另有登录、领养、权限说明三个引导流程。领养完成后不再展示宠物选择页。

## 八、核心数据对象

| 数据对象 | 关键字段 |
| --- | --- |
| 用户 | 用户编号、昵称、头像、简介、状态、创建时间 |
| 宠物 | 宠物编号、用户编号、固定形象编号、名称、好感度、领养时间 |
| 每日好感记录 | 用户编号、日期、聊天奖励状态、互动计数、当日增加值 |
| 对话会话 | 会话编号、用户编号、有限上下文、创建时间、更新时间 |
| 对话消息 | 消息编号、会话编号、角色、内容、审核状态、时间 |
| 动态 | 动态编号、作者编号、正文、审核状态、可见状态、时间 |
| 动态图片 | 图片编号、动态编号、存储地址、排序、审核状态 |
| 点赞 | 用户编号、动态编号、时间；两者组成唯一约束 |
| 评论 | 评论编号、动态编号、作者编号、正文、审核状态、时间 |
| 举报 | 举报编号、举报人、目标类型、目标编号、原因、处理状态 |
| 拉黑 | 发起用户、被拉黑用户、时间；两者组成唯一约束 |
| 管理日志 | 管理员、操作类型、目标、操作前后摘要、时间 |

宠物表必须对“用户编号”建立唯一约束。这是“只能领养一只”的最终数据保障，不能只依赖客户端按钮状态。

## 九、非功能要求

### 9.1 安全与隐私

- 模型、对象存储和短信等服务密钥只保存在服务端。
- 全部网络接口使用加密传输，登录凭证使用系统安全能力保存。
- 只申请实现功能所必需的安卓权限，并在申请前解释用途。
- 聊天记录的保存范围、保存时间、删除方式需要在隐私政策中写明。
- 图片上传前移除不必要的定位等元数据。
- 日志不得记录完整凭证、隐私文本或模型密钥。

### 9.2 性能与稳定性

- 普通页面操作应及时响应，动态列表使用分页与图片缩略图。
- 悬浮窗服务被系统回收后不进行无限拉起。
- 弱网、断网、重复提交和接口超时均需有可恢复状态。
- 发布、领养、点赞和好感度增加接口必须具备幂等或唯一约束。

### 9.3 兼容性与可访问性

- 建议最低支持安卓 8.0，重点测试安卓 10 至当前主流版本。
- 适配刘海屏、挖孔屏、手势导航、横竖屏和不同显示缩放。
- 文字支持系统字体缩放；按钮和悬浮头像保留足够点击区域。
- 小猫反馈不能只靠颜色表达，同时提供文字或图形反馈。

## 十、首版明确不做

- 第二种宠物或同时领养多只宠物；
- 宠物换装、成长、进化、等级技能；
- 小游戏；
- 宠物交易、道具商城和虚拟货币；
- 私信、群聊、直播；
- 开机自启和无法关闭的强制悬浮；
- 复杂推荐算法；
- 好友对战、排行榜和签到惩罚。

## 十一、首版验收条件

1. 新用户可以完成登录、领养和命名，重复操作始终只有一只宠物。
2. 授权后小猫可稳定悬浮于其他应用上方，能够拖动、点击、隐藏和关闭。
3. 拒绝悬浮权限后，应用不会崩溃，应用内聊天和社区仍可使用。
4. 用户完成当天有效聊天后，好感度只按规则增加一次。
5. 用户当天互动超过奖励上限后，不再增加好感度。
6. 重新登录或更换设备后，宠物与好感度以服务端记录正确恢复。
7. 用户可以发布、浏览、点赞、评论、删除、举报和拉黑。
8. 违规内容能够进入审核或举报处理流程，管理员操作可追踪。
9. 断网、超时、模型故障、图片上传失败等情况都有清晰提示和重试路径。
10. 应用内没有换装、成长和小游戏入口或残留流程。

## 十二、开发前待确认项

这些问题不妨碍制定计划，但会影响正式实现与成本：

1. 产品正式名称、图标和小猫视觉风格。
2. 登录方式：手机号、邮箱还是第三方账号。
3. 社区是否允许图片，以及每条动态最多允许几张。
4. 对话模型供应方、预算、每人每日消息上限和聊天记录保存期限。
5. 好感度是否直接显示数值，以及聊天、互动的最终奖励数值。
6. 目标发布渠道；不同应用商店对悬浮窗、前台服务和用户生成内容的审核要求可能不同。
