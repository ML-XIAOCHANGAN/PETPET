# PETPET 安卓虚拟宠物社区开发计划

> 文档状态：首版实施建议  
> 编写日期：2026-08-09  
> 前置文档：[01_需求分析.md](./01_需求分析.md)

## 一、交付目标

完成一个可以内测的安卓首版，交付内容包括：

- 安卓客户端；
- 业务服务端；
- 社区内容管理后台；
- 数据库、对象存储和部署配置；
- 小猫固定头像及必要反馈动画；
- 接口文档、测试报告、隐私清单和发布说明。

首版完成的标志不是页面全部画完，而是“领养一只猫—悬浮陪伴—聊天互动增加好感—进入社区交流—内容可治理”这一闭环稳定可用。

## 二、推荐技术方案

### 2.1 安卓客户端

- 开发语言：`Kotlin`；
- 界面：`Jetpack Compose`；
- 架构：单向数据流与分层架构；
- 依赖注入：`Hilt`；
- 网络：`Retrofit` 与 `OkHttp`；
- 本地缓存：`Room`；
- 轻量配置：`DataStore`；
- 图片加载：`Coil`；
- 异步任务：协程与 `WorkManager`；
- 悬浮层：`WindowManager`、`TYPE_APPLICATION_OVERLAY` 与受控前台服务。

建议最低系统版本为安卓 8.0。悬浮窗先制作独立技术样例，尽早验证不同系统版本和厂商系统的表现。

### 2.2 服务端

- 接口服务：`Spring Boot`；
- 数据库：`PostgreSQL`；
- 缓存及限流：`Redis`；
- 图片存储：兼容 `S3` 协议的对象存储；
- 接口风格：版本化 `REST` 接口；
- 实时能力：首版不强依赖长连接，站内消息可先采用分页拉取；
- 部署：`Docker` 容器、反向代理、自动化迁移和分环境配置。

对话模型、文本审核、图片审核、短信和对象存储均通过服务端适配层接入，避免将业务绑定到单一供应方。

### 2.3 管理后台

- 使用成熟的网页管理框架实现；
- 只面向运营和审核人员，不与普通用户界面混用；
- 管理账号启用强密码、权限分级和操作审计；
- 首版优先保证举报处理、内容下架、用户封禁和配置管理。

## 四、关键技术设计

### 4.1 只能领养一只

客户端禁用重复领养按钮只是体验层措施，服务端还需同时完成：

1. 领养接口携带幂等标识；
2. 服务端在事务中检查当前账号；
3. 宠物表对用户编号建立唯一索引；
4. 并发请求触发唯一冲突时返回已存在的宠物，而不是创建新记录；
5. 客户端以服务端返回的宠物信息刷新本地状态。

### 4.2 好感度结算

好感度必须由服务端结算，建议将规则做成可配置参数：

```text
聊天奖励条件：当天完成三轮有效对话
聊天每日奖励：5 点
互动单次奖励：1 点
互动每日计奖上限：5 次
每日理论上限：10 点
```

每日记录以业务约定时区计算。接口需要防止重复请求、修改本地时间和并发点击造成重复加分。聊天内容是否有效，可结合非空、长度、重复率、发送间隔和风险审核结果判断。

### 4.3 悬浮窗生命周期

1. 用户在应用内开启悬浮小猫。
2. 应用检测系统悬浮权限。
3. 未授权时展示用途说明，再跳转系统设置页。
4. 授权后启动受控前台服务并创建悬浮视图。
5. 服务保存小猫位置和显示状态。
6. 点击展开轻量操作菜单；进入聊天时打开应用内页面或小型对话面板。
7. 用户点击关闭、撤销权限或退出账号时，立即移除悬浮视图并停止对应服务。

不得制造无法关闭、遮挡系统界面或反复自动弹出的悬浮体验。前台服务的声明、通知和启动时机需根据目标安卓版本逐项核对。

### 4.4 对话服务

服务端负责：

- 组合固定的小猫性格提示和有限历史消息；
- 过滤输入与输出风险内容；
- 隐藏模型密钥；
- 控制单用户频率、每日额度、超时和费用；
- 记录调用结果、耗时和错误码，但不在普通日志中写出完整私密对话；
- 模型失败时返回可识别的降级状态。

客户端负责消息展示、发送状态、失败重试和本地短期缓存，不直接连接模型供应商。

### 4.5 社区安全

社区发布链路建议为：

```text
用户提交 → 参数和频率检查 → 文本/图片审核 → 发布或进入复核 → 用户可举报 → 管理员处理 → 留存审计
```

拉黑、删除、封禁和内容下架必须在服务端生效，不能只在当前设备隐藏。所有管理操作需要记录操作者、原因和时间。

## 五、首版接口清单

接口命名可在设计阶段调整，首版至少覆盖以下能力：

| 模块 | 能力 |
| --- | --- |
| 认证 | 注册、登录、刷新凭证、退出、注销 |
| 用户 | 获取及修改个人资料、查看用户主页、拉黑与解除拉黑 |
| 宠物 | 获取我的宠物、领养、修改宠物名字 |
| 好感度 | 查询当前值和当天奖励进度、提交互动、结算聊天奖励 |
| 聊天 | 创建或获取会话、发送消息、获取有限历史、清除历史 |
| 动态 | 列表、详情、发布、删除、点赞、取消点赞 |
| 评论 | 列表、发布、删除 |
| 举报 | 提交举报、查询自己的处理结果 |
| 图片 | 获取上传凭证或受控上传、完成上传确认 |
| 消息 | 站内消息列表、未读数、标记已读 |
| 配置 | 客户端版本、功能开关、好感规则和社区限制 |
| 管理 | 用户处置、内容处置、举报处理、配置和审计查询 |

正式编码前需通过接口文档明确请求结构、错误码、分页规则、幂等方式和时间格式。

## 六、开发阶段与排期

以下为两名开发人员并行、设计和测试兼职参与时的八周估算。若由一人独立完成，建议预留十二至十四周。

| 阶段 | 时间 | 主要工作 | 阶段成果 |
| --- | --- | --- | --- |
| 第一阶段：需求与技术预研 | 第 1 周 | 确认待定项、低保真原型、数据模型、悬浮窗样例、模型调用样例 | 可评审原型与技术验证报告 |
| 第二阶段：工程基础 | 第 2 周 | 客户端骨架、服务端骨架、数据库迁移、登录、环境配置、持续集成 | 可登录的端到端空壳版本 |
| 第三阶段：领养与悬浮 | 第 3 周 | 唯一领养、宠物主页、权限引导、悬浮服务、拖动与关闭 | 小猫可领养并稳定悬浮 |
| 第四阶段：聊天与好感 | 第 4 周 | 对话服务、预设降级、互动动画、每日结算、防重复与限流 | 陪伴核心闭环可用 |
| 第五阶段：社区主体 | 第 5 周 | 动态、图片、点赞、评论、个人主页、分页与缓存 | 基础社区闭环可用 |
| 第六阶段：治理与后台 | 第 6 周 | 举报、拉黑、审核、后台处置、审计、站内消息 | 用户生成内容具备治理能力 |
| 第七阶段：联调与加固 | 第 7 周 | 弱网、异常、权限、并发、安全、性能、隐私和兼容性修复 | 候选内测版本 |
| 第八阶段：内测与交付 | 第 8 周 | 多机型回归、灰度内测、问题修复、文档和发布材料 | 首个可交付内测版本 |

## 七、详细任务顺序

### 第一里程碑：产品和技术可行

- 确认登录方式、社区图片规则、模型供应方和预算；
- 完成首页、领养、宠物页、社区、发布页的低保真原型；
- 在至少三种安卓版本上验证悬浮、拖动、关闭和进程回收；
- 验证一次模型调用、超时和降级；
- 评审数据模型、权限清单和内容治理流程。

### 第二里程碑：陪伴闭环可用

- 完成注册登录和用户资料；
- 完成唯一领养及宠物命名；
- 完成悬浮小猫及权限引导；
- 完成文本聊天和本地预设降级；
- 完成互动和好感度结算；
- 编写领养并发、每日边界和权限撤销自动化测试。

### 第三里程碑：社区闭环可用

- 完成动态列表、详情、发布和删除；
- 完成图片上传压缩、审核和失败恢复；
- 完成点赞、评论、举报和拉黑；
- 完成管理后台的内容下架、用户封禁与操作审计；
- 完成社区频率限制和敏感内容处理。

### 第四里程碑：达到内测质量

- 完成安卓版本和主要厂商机型测试；
- 完成断网、弱网、服务异常、重复提交和会话过期测试；
- 检查耗电、内存、悬浮窗长期运行和图片列表性能；
- 完成隐私政策、权限用途、账号注销和数据删除流程；
- 建立崩溃、接口错误、模型成本和审核积压监控；
- 灰度发布并收集内测反馈。

## 八、测试计划

### 8.1 功能测试重点

- 同一账号连续、并发和跨设备领养，最终只有一只宠物；
- 当天重复聊天或互动不会突破奖励上限；
- 跨日、修改手机时间、跨时区和服务端重试不会错误加分；
- 悬浮权限允许、拒绝、撤销后状态正确；
- 拖动悬浮头像不会误触，关闭后不残留窗口；
- 发帖、点赞和评论重复提交不会产生重复记录；
- 举报、拉黑和封禁在重新登录后仍然生效。

### 8.2 兼容性测试重点

- 安卓 8.0、10、12、13、14、15、16 的代表性设备或模拟器；
- 主流厂商系统的后台限制、悬浮权限入口和通知行为；
- 刘海屏、挖孔屏、横屏、分屏、深色模式、字体放大；
- 从省电模式、锁屏、系统回收、升级安装和重启恢复。

### 8.3 安全测试重点

- 登录凭证泄露、越权读取或修改他人宠物；
- 伪造好感度、刷点赞、刷评论和批量发帖；
- 上传非图片、超大文件、恶意文件和含隐私元数据的图片；
- 提示注入诱导小猫暴露服务端配置；
- 管理后台弱权限、越权操作和审计记录缺失；
- 日志、崩溃报告和分析平台误收集聊天隐私。

## 九、主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 不同厂商限制悬浮或后台服务 | 小猫消失、通知异常或耗电 | 第一周先做多机型样例；提供清楚的系统设置说明；允许应用内使用 |
| 应用商店审核限制 | 无法按计划发布 | 提前确定发布渠道；核对悬浮、前台服务、通知和用户生成内容政策 |
| 对话模型费用增长 | 运营成本失控 | 每日额度、限流、缓存、短上下文、模型可替换和用量告警 |
| 模型输出不安全 | 用户伤害和合规风险 | 输入输出审核、固定安全提示、敏感场景降级和举报入口 |
| 社区违规内容 | 投诉、下架和运营压力 | 自动审核、人工后台、举报、拉黑、封禁和审计闭环 |
| 好感度被刷 | 社交数据失真 | 服务端结算、幂等、每日记录、频率限制和异常检测 |
| 图片存储与流量增长 | 成本和加载速度问题 | 数量限制、客户端压缩、多尺寸缩略图、生命周期和配额 |
| 范围继续扩张 | 首版延期 | 以需求文档“不做清单”为边界，新增功能进入后续版本池 |

## 十、质量门槛

进入公开测试前至少满足：

- 所有首版验收条件通过；
- 不存在可稳定复现的崩溃、严重越权或数据重复问题；
- 悬浮小猫可随时关闭，权限撤销后无残留；
- 模型故障不会阻断应用主要页面；
- 举报内容可在后台查看和处置；
- 数据库可备份、恢复并执行版本迁移；
- 监控能够发现崩溃、接口高错误率、模型超预算和审核积压；
- 隐私政策、服务条款、社区规范和账号注销路径齐备。

## 十一、后续版本候选

首版稳定后，基于真实使用数据决定是否加入：

- 关注用户与关注动态流；
- 更多小猫表情或动作，但不改变固定宠物种类；
- 公开分享部分聊天片段，必须由用户主动选择并脱敏；
- 社区话题和搜索；
- 更细的通知控制；
- 无障碍与平板体验增强。

换装、成长和小游戏仍不自动进入后续版本，除非产品方向被明确修改。
